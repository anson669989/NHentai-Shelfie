### 1.2 EhTagTranslation/Database（標籤翻譯資料來源）

以 GitHub API 與實際下載檔案確認：

- 儲存庫：<https://github.com/EhTagTranslation/Database>，預設分支 `master`。

- 授權：`LICENSE.md` 為「署名-非商业性使用-相同方式共享 3.0 中国大陆」＝ **CC BY-NC-SA 3.0（CN）**。使用時要標示來源與授權；NC 代表本 App 不可拿這份資料做商業用途。

- 發佈頻率：很高。查詢當下最新是 `v7.29838.1`（2026-11-14 07:02 UTC），同一天 3 分鐘內就有 3 個 release。**不要寫死版本號**，一律用 `releases/latest/download/<檔名>`。

- 每個 release 有 16 個檔案：`db.{ast,full,html,raw,text}.{js,json,json.gz}` 共 15 個，加上 `sha`。

- 本 App 用 **`db.text.json.gz`**（純文字版，名稱不含 HTML／Markdown）：壓縮後 **1,317,621 bytes**，解壓後 `db.text.json` 為 **4,289,337 bytes**。

- `sha` 檔：40 bytes，內容是資料的 commit sha（與 JSON 內 `head.sha` 相同），可用來判斷資料有沒有更新。

- 下載網址會轉址兩次：`github.com/.../releases/latest/download/X` → `github.com/.../releases/download/<tag>/X` → `release-assets.githubusercontent.com/...`。最後回應是 `Content-Type: application/octet-stream`，沒有 `Content-Encoding`（`.gz` 要自己解壓）。

- JSON 結構（`db.text.json`）：

  ```
  {
    "repo": "https://github.com/EhTagTranslation/Database",
    "head": { "sha": "<40 位十六進位>", "message": "...", "author": {...}, "committer": {...} },
    "version": 7,
    "data": [
      { "namespace": "female", "frontMatters": {...}, "count": 613,
        "data": { "big breasts": { "name": "巨乳", "intro": "...", "links": "" }, ... } },
      ...
    ]
  }
  ```

- `data` 共 13 個 namespace，筆數：`rows` 13、`reclass` 11、`language` 87、`parody` 3,003、`character` 10,115、`group` 14,376、`artist` 15,850、`cosplayer` 179、`male` 575、`female` 613、`mixed` 23、`other` 62、`location` 8，合計 44,915。

- key（原文標籤）全部是小寫、無頭尾空白；`name` 是簡體中文（作者／社團多半是日文原名），沒有空字串、沒有換行。部分 `name` 含 emoji（359 筆，例如「丧尸🧟‍♀️」）。

- nhentai 的 `tag` 類型沒有 namespace，要對到 `female`／`male`／`mixed`／`other`／`location` 五個 namespace：合併後有 **774** 個不重複的 key。`female` 與 `male` 有 489 個相同的 key，其中 19 個翻譯不同（例如 `oyakodon`：母女丼／父子丼）；另有 18 個 key 同時出現在 `female`／`male`／`mixed`（例如 `group`、`incest`、`twins`）。

- 只取 tag／artist／group 三類共 774 + 15,850 + 14,376 = **31,000** 筆；其中作者／社團有 5,431 筆「翻譯與原文相同」（可略過不存）、17,046 筆的名稱含日文假名。

- 用專案內的測試資料驗證命中率：`tests/fixtures/gallery-api-v2.json` 的 tag／artist／group 共 50 個，命中 45 個；`gallery-api-v2-webp.json` 3 個全中。沒命中的顯示原文即可。

- `intro`（說明文字）另有 EHWiki／維基百科／萌娘百科的授權條款，**本 App 只取 `name`，不要存 `intro` 與 `links`**。

## 2. 整體設計

### 2.1 資料模型：schema v4

在 `src/services/db.js` 的 `MIGRATIONS` **陣列尾端**新增一個元素（v4），舊版本一個字都不改。遷移前的自動備份（`backupDatabase`）沿用現有機制，不必改 `migrate()`。

v4 的 SQL（照抄；風格比照 v1–v3：每個語句以 `;` 結尾並換行、SQL 字串內不放註解、字串常值內不放分號）：

```sql
ALTER TABLE folders ADD COLUMN kind TEXT NOT NULL DEFAULT 'user';
UPDATE folders SET name = name || '_' WHERE name IN ('::nhs-unread::', '::nhs-fav::');
INSERT INTO folders(name, sort_order, sort_mode, created_at, kind) VALUES ('::nhs-unread::', -2, 'added_desc', 0, 'unread');
INSERT INTO folders(name, sort_order, sort_mode, created_at, kind) VALUES ('::nhs-fav::', -1, 'added_desc', 0, 'fav');
CREATE TABLE IF NOT EXISTS folder_separators (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT NOT NULL DEFAULT '',
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL
);
CREATE TABLE IF NOT EXISTS tag_translations (
  type  TEXT NOT NULL,
  name  TEXT NOT NULL,
  zh_cn TEXT NOT NULL,
  zh_tw TEXT NOT NULL,
  PRIMARY KEY (type, name)
);
```

說明：

- `folders.kind`：`'user'`（使用者資料夾，舊資料全部是這個）／`'unread'`（未讀）／`'fav'`（典藏）。
- 第 2 行是保險：萬一使用者剛好有同名資料夾，先改名避免 `UNIQUE` 衝突讓遷移失敗（實際上不可能發生）。
- 系統資料夾的 `sort_order` 是負數，所以 `ORDER BY sort_order, id` 自然排在最前面（使用者資料夾的 `sort_order` 從 1 開始）。
- `folder_separators`：分隔線。**獨立一張表**，不放進 `folders`（理由見 2.2）。
- `tag_translations`：標籤翻譯。`type` 是 nhentai 的類型（`tag`／`artist`／`group`），`name` 是原文（小寫），`zh_cn` 簡體、`zh_tw` 繁體（台灣用語）。
- 舊使用者升級後：所有書、資料夾、關聯都原封不動；多了兩個空的系統資料夾、兩張空表。**現有的書不會被標成未讀**。

> **陷阱：v4 一旦 push 到 main 並被裝到手機，就視同已發佈，不可再改。** 使用者會在各階段之間安裝 CI 建出來的 APK 測試。所以 v4 的內容要在階段 A 一次定案（上面已包含階段 B、E 需要的表）。之後若發現還缺欄位，只能再加 v5。

不需要新表的資料：

- 快速分享的設定、標籤翻譯的狀態 → 存在現有的 `settings` 表（2.3）。
- 快速分享「還沒進資料庫的收件匣」→ 存在 Android 原生的 SharedPreferences（2.4），不進 SQLite。

### 2.2 系統資料夾與分隔線的表示方式

**四個系統資料夾**，固定在所有資料夾清單的最上方，順序固定：全部 → 未分類 → 未讀 → 典藏。都不能改名、刪除、排序。

| 名稱   | 表示方式                                  | 介面用的鍵    | 一本書是否屬於它                                        |
| ------ | ----------------------------------------- | ------------- | ------------------------------------------------------- |
| 全部   | 虛擬（維持現況）                          | `'all'`       | 所有書                                                  |
| 未分類 | 虛擬（維持現況，**定義改變**）            | `'uncat'`     | 沒有加入任何 `kind = 'user'` 的資料夾（系統資料夾不算） |
| 未讀   | `folders` 表裡 `kind = 'unread'` 的那一列 | 該列的數字 id | `book_folders` 有關聯                                   |
| 典藏   | `folders` 表裡 `kind = 'fav'` 的那一列    | 該列的數字 id | `book_folders` 有關聯                                   |

- 未讀、典藏是「真的資料夾」，沿用 `book_folders`，所以加入／移除／篩選／本數／各自記住排序（`folders.sort_mode`）全部沿用現有程式，只是用 `kind` 找它、名稱由介面翻譯。

- 一本書可以同時是「未分類＋未讀」「未分類＋典藏」「未讀＋典藏」或三者都是，也可以同時在使用者資料夾裡；彼此獨立。

- 「未讀」沒有自動判斷：加入時依設定放進去，之後只有使用者手動移除（在未讀資料夾裡用「從『未讀』移除」，或在分類選單取消勾選）才算已讀。

- 系統資料夾在資料庫裡的 `name`（`::nhs-unread::`、`::nhs-fav::`）只是佔位字串，**任何畫面都不可以直接顯示它**；顯示名稱一律經過 `folderLabel()`（階段 A 新增）取 `t('folder.unread')`／`t('folder.fav')`。

- 新的未分類條件（SQL 片段，`b` 是 books 的別名）：

  ```sql
  NOT EXISTS (SELECT 1 FROM book_folders bf JOIN folders f ON f.id = bf.folder_id
              WHERE bf.gallery_id = b.gallery_id AND f.kind = 'user')
  ```

**分隔線**：存在 `folder_separators`，和使用者資料夾**共用同一個 `sort_order` 編號序列**（兩張表的列混在一起排序）。

- 為什麼不放進 `folders`：(1) `book_folders` 的外鍵只指向 `folders`，分隔線放別張表就「從結構上」不可能被拿來分類書；(2) `folders.name` 有 `UNIQUE`，分隔線需要允許重複名稱與空白名稱；(3) SQLite 拿掉 `UNIQUE` 要重建資料表，而在 `foreign_keys = ON` 下 `DROP TABLE folders` 會連帶刪掉 `book_folders`，風險太高。
- 介面與服務層一律以「項目鍵」識別：資料夾 `f:<id>`、分隔線 `s:<id>`。
- 合併規則（純函式 `mergeFolderItems`）：先放系統資料夾（未讀、典藏），再放「使用者資料夾＋分隔線」依 `sort_order` 由小到大；`sort_order` 相同時資料夾在前、再依 id。
- 新建的資料夾或分隔線接在最後（`sort_order` = 兩張表的最大值 + 1）。
- 分隔線只是視覺工具：不能勾選、沒有本數、不出現在任何「書屬於哪些資料夾」的資料裡；但在**所有**列出資料夾的清單裡都要依順序顯示（收藏頁資料夾篩選、單本分類、新增頁選資料夾、多選批次分類、快速分享的自動加入設定、管理資料夾）。

### 2.4 快速分享的原生架構

**目標**：設定為「直接收藏」時，在瀏覽器按分享 → 選 NH Shelfie → 畫面留在瀏覽器，跳出一個提示（成功收藏／重複收藏／非 nhentai 書籍）。

**核心決定：原生端不碰 SQLite。** 理由：App 的資料庫由 `@capacitor-community/sqlite` 開啟，同一個行程裡若再用 Android 內建的 SQLite 去開同一個檔案，檔案鎖會互相失效，有毀損資料庫的風險；而且規則是「`library.js` 是唯一碰 SQLite 的地方」。所以改用「收件匣」：

```
瀏覽器分享
   │  ACTION_SEND text/plain
   ▼
ShareReceiverActivity（新，放在 nh-webfetch 外掛；無畫面，處理完立刻 finish）
   │ 讀 SharedPreferences「nh_quick_share」的 mode
   ├─ mode = open（或從未設定）──► 把同一份分享內容轉給 MainActivity（明確指定元件）
   │                                └► 之後完全是現有流程（外掛 captureShare → 新增頁填入 ID）
   └─ mode = quick
        1. 從文字取出 nhentai 的 ID（規則同 JS 的 extractNhGalleryId）
           └ 取不到 ──► Toast「非 nhentai 書籍」
        2. ID 已在「已收藏 ID 快照」或「收件匣」裡 ──► Toast「重複收藏 #id」（什麼都不改）
        3. 否則把 {id, at} 寫進收件匣 ──► Toast「成功收藏 #id」
           └ 若 App 還活著：通知外掛發出 quickShareReceived 事件
   ▼
App 下次啟動／回到前景／收到事件時（JS，library.drainQuickShares）
   讀收件匣 → 還沒收藏的 ID 以「先存、後查」寫入資料庫（meta_pending，加入時間用分享當下的時間，
   資料夾用設定的自動加入清單）→ 向原生確認已處理（清掉收件匣）→ 背景佇列照常補書名與封面
```

細節：

- **分享選單只有一個 NH Shelfie 入口**。`ACTION_SEND` 的 intent-filter 從 `MainActivity` 搬到 `ShareReceiverActivity`，由它依設定決定行為（所以切換設定就能切換兩種功能）。

- `ShareReceiverActivity`：繼承 `android.app.Activity`（不是 AppCompat），主題 `@android:style/Theme.NoDisplay`，`exported="true"`、`excludeFromRecents="true"`、`noHistory="true"`、`taskAffinity=""`；不呼叫 `setContentView`。宣告在**外掛的** `AndroidManifest.xml`（manifest 合併會自動併進 App），不設定 `android:label`／`android:icon`（沿用 App 的名稱與圖示）。

- 原生儲存（`QuickShareStore`，SharedPreferences 名稱 `nh_quick_share`，所有讀寫以同一把鎖同步，寫入用 `commit()`）：

  | 鍵                                                       | 內容                                                                  | 誰寫                                              |
  | -------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------- |
  | `mode`                                                   | `open`／`quick`                                                       | JS（經外掛 `setQuickShareConfig`）                |
  | `hosts`                                                  | 允許的網域，逗號分隔（預設 `nhentai.net`）                            | JS                                                |
  | `ids`                                                    | 已收藏的 ID，逗號分隔（快照）                                         | JS                                                |
  | `msg_saved`／`msg_duplicate`／`msg_not_nh`／`msg_failed` | 提示文字（含 `{id}`），目前介面語言                                   | JS                                                |
  | `inbox`                                                  | JSON 陣列字串 `[{"id":228922,"at":1794650000000}, ...]`，最多 1000 筆 | 原生（Activity 加入、外掛 `ackQuickShares` 移除） |

- 提示文字由 JS 從 `locales.js` 取出後推給原生，所以四種語言仍只維護在 `locales.js`。Java 內另放英文備援字串（從未同步過設定時用）。

- 「已收藏 ID 快照」由 JS 在這些時機整份重推：App 啟動完成、`quickAdd` 新增了書、`deleteBooks`、`changeBookId`、`commitCsvImport`、`drainQuickShares` 之後；切換 `share_mode`、切換語言時也要重推設定。快照可能比資料庫慢一步（例如 App 被強制關閉前剛刪書），最壞情況只是提示文字不準一次，資料不會錯：真正寫入時 JS 會再查一次資料庫，已收藏的書**完全不動**。

- 外掛新增三個方法與一個事件（JS 端只有 `nhSource.js` 可以呼叫）：

  - `setQuickShareConfig({ mode, hosts, ids, msgSaved, msgDuplicate, msgNotNh, msgFailed })`
  - `peekQuickShares()` → `{ items: [{ id, at }] }`（只讀不清）
  - `ackQuickShares({ ids: [...] })`（把這些 id 從收件匣移除）
  - 事件 `quickShareReceived`

- 先 peek、寫完資料庫才 ack：中途當掉最多重做一次，而重做是安全的（已收藏就跳過）。

- 不新增 Android 權限、不新增 Capacitor 外掛、不加背景服務。**書名與封面要等使用者下次打開 App 才會補**（背景佇列只在前景執行，這是既有限制）。

### 2.5 標籤翻譯：儲存與更新流程

**儲存**：`tag_translations(type, name, zh_cn, zh_tw)`，只存 tag／artist／group 三類、且「翻譯和原文不同」的項目（約 2.5 萬筆）。每次更新都是**整批取代**（一個交易：先 `DELETE` 全部，再分批 `INSERT`，最後寫 `tagtr_*` 設定）。

**對應規則**（純函式 `parseTagDb`）：

- nhentai `artist` ← EhTagTranslation `artist`；`group` ← `group`。
- nhentai `tag` ← 依序找 `mixed` → `female` → `male` → `other` → `location`，**先找到的為準**（`mixed` 的翻譯是中性說法，所以排第一）。
- 其他 namespace（`rows`、`reclass`、`language`、`parody`、`character`、`cosplayer`）不存。
- key 一律 `trim().toLowerCase()`；`name` 去頭尾空白，空字串、超過 100 字、或和 key 相同（不分大小寫）的略過。

**簡 → 繁**：更新時就把兩種寫法都算好存進資料庫（`zh_cn` 原樣、`zh_tw` 用 opencc-js 的 `cn → twp` 轉換），切換介面語言時不必重算。名稱含日文假名（平假名／片假名）的視為日文名稱，**不轉換**（`zh_tw = zh_cn`）。

**顯示**：只影響收藏頁（「資料夾」分頁）的標籤篩選 `TagFilter`。

- `tag_translate = '1'` 且介面語言是 `zh-TW` → 顯示 `zh_tw`；是 `zh-CN` → 顯示 `zh_cn`；英文／日文介面或開關關閉 → 一律顯示原文。
- 沒有翻譯的標籤顯示原文。
- 打字搜尋同時比對原文與翻譯（打 `glasses` 或「眼鏡」都找得到）。

**更新流程**（`library.updateTagTranslations`）：

1. 觸發時機：App 啟動完成、回到前景、打開開關、按設定頁「立即更新」。前三種要同時滿足「開關開啟」與「距離 `tagtr_checked_at` 已滿 24 小時」（或資料表是空的）；失敗後 1 小時內不重試（記在記憶體即可）。同時間只跑一個。不擋啟動、不擋畫面。
2. 用原生 HTTP 取 `https://github.com/EhTagTranslation/Database/releases/latest/download/sha`。內容是 40 位十六進位且等於 `tagtr_sha` → 資料沒變，只更新 `tagtr_checked_at`，結束。取不到或格式不對 → 當作不知道，繼續下一步。
3. 下載 `.../releases/latest/download/db.text.json.gz` 到快取目錄（`Filesystem.downloadFile`，先 `ensureParentDir`），讀成位元組，用瀏覽器內建的 `DecompressionStream('gzip')` 解壓成文字（解壓後超過 30 MB 就中止）。
   - WebView 沒有 `DecompressionStream`（很舊的 WebView）→ 改下載未壓縮的 `db.text.json`，以 UTF-8 文字讀入。
4. `JSON.parse` → `parseTagDb`（結構不對就丟錯，舊資料保留）→ 動態載入 opencc-js 轉出 `zh_tw` → 一個交易整批取代並寫入 `tagtr_sha`／`tagtr_count`／`tagtr_updated_at`／`tagtr_checked_at` → 刪暫存檔 → `bump()` 讓畫面重新查詢。
5. 任一步失敗：保留舊資料、設定頁顯示「更新失敗，之後會自動重試」，不跳對話框打擾使用者。

**網路規則**：

- 這是 nhentai 以外的**第一個**對外連線。新增 `src/services/tagDbSource.js` 作為「唯一對 GitHub 發請求的地方」，不經 nhSource 的兩條隊伍（不是 nhentai 的請求）。
- 網址是寫死的常數（兩個），只准 `https://github.com/EhTagTranslation/Database/releases/latest/download/` 開頭；轉址由原生 HTTP 自動跟隨（目的地是 `*.githubusercontent.com`）。
- **不可用 `fetch()`**（CSP `connect-src 'self'` 會擋，也不要為此放寬 CSP）。
- 帶 `NH-Shelfie/<版本>` 的 User-Agent（沿用 nhSource 的 `appUserAgent`，把它改成 export）。不送出任何使用者資料。

### 2.6 CSV 格式 v2（向下相容）

```
gallery_id,folders,note,added_at,system
#nh-shelfie,2,,,
#folder,收藏,added_desc,,
#separator,標籤,,,
#folder,巨乳,title,,
#separator,,,,
#setting,share_mode,quick,,
#setting,share_auto_system,unread,,
#setting,share_auto_folders,收藏|巨乳,,
177013,收藏|巨乳,備註文字,2026-11-06T10:55:00+08:00,unread|fav
228922,,,2026-11-06T11:02:00+08:00,
```

- **書的列**：多一欄 `system`，內容是 `unread`、`fav` 以 `|` 相接（固定英文代號，不隨語言變）。`folders` 欄只放使用者資料夾名稱（和舊版相同）。
- **中繼列**：第一欄以 `#` 開頭、後面是英文小寫代號，放在標頭之後、所有書之前：
  - `#nh-shelfie,2`：格式版本。
  - `#folder,<名稱>,<sort_mode>`、`#separator,<名稱>`：使用者資料夾與分隔線，**依畫面上的順序**一列一個（沒有書的空資料夾也會被備份）。
  - `#setting,<鍵>,<值>`：目前只有三個鍵——`share_mode`、`share_auto_system`（`unread`／`fav`）、`share_auto_folders`（使用者資料夾名稱）。`share_auto_folders` 設定是空字串（未設定）時，後兩列不輸出。
  - 不認得的 `#xxx` 列一律安靜略過（為以後擴充留空間），不算進「跳過 N 筆」。
- 名稱欄位照舊經過「防公式」與引號處理。
- **舊版 CSV 匯入新版 App**：沒有 `system` 欄 → 不加入任何系統資料夾；沒有中繼列 → 資料夾照舊接在最後、不建分隔線、不動設定。
- **新版 CSV 匯入舊版 App**：多的欄被忽略；中繼列會被當成「ID 無效」跳過（預覽會多幾列跳過的訊息），書照常匯入。
- **匯入時的還原規則**（純函式 `planLayoutImport`）：
  - 資料夾以名稱比對，本機沒有的才建立。
  - 分隔線沒有唯一識別，以「同名的第幾條」比對：CSV 裡第 k 條叫 X 的分隔線，對應本機第 k 條叫 X 的；本機不夠才新建。所以同一個檔案匯入兩次不會多出分隔線。
  - 順序：CSV 列出的項目依 CSV 的順序排在前面；本機原有但 CSV 沒列的接在後面，維持原本的相對順序。
  - `#setting` 直接覆蓋本機設定（資料夾名稱換成 id；找不到的名稱略過）。
  - 已收藏的書照舊整列跳過（不合併它的資料夾或未讀狀態）。
- 匯出前先處理快速分享的收件匣（呼叫 `drainQuickShares`），確保剛分享的書也在備份裡。

### 2.7 對話框元件（`ui.js`／`DialogHost.vue`）的擴充

- **選單結構**：`.sheet` 改成「固定的標題列 `.sheet-head`」＋「會捲動的 `.sheet-body`」＋「固定在底部的 取消／完成 按鈕」。不再用 `position: sticky` ＋負 margin。拖曳排序的捲動容器跟著改成 `.sheet-body`。
- **標題列右側按鈕** `headAction: { icon: 'refresh', label, value }`：灰色小圖示鈕，點了關閉選單並回傳 `value`。
- **分隔線列** `{ separator: true, label }`：置中的灰色文字，左右各一條線；`label` 是空字串時只有一條線。中間的文字不可點、不可勾選。若同時帶 `more: true, drag: true`（管理資料夾與收藏頁的資料夾篩選都會用到）則左邊有 ≡、右邊有 ⋯，可以和資料夾列混在一起拖曳。
- **多選清單（checklist）**的項目也支援 `{ separator: true, label }`。
- 多選選單（`multi`）沿用現有機制：點一列呼叫 `multi.toggle(value)`、選單不關、最下方按鈕是「完成」。

## 3. 自行決定的細節（請使用者審閱）

> 以下是清單沒寫到、由規劃者依照 App 現有風格決定的事。前 5 項影響比較大，請優先看。

**影響較大**

1. **新增一個程式庫 `opencc-js`**（簡體轉繁體台灣用語）。它是純 JavaScript 的套件，不是 Capacitor 外掛、不需要權限，但會讓 App 多約 1.1 MB（只在更新翻譯時才載入）。理由：翻譯資料每天更新，一定要在手機上轉換；自己寫對照表無法做到台灣用語。**若不想加**：替代方案是繁體介面也直接顯示簡體。
2. **分享選單維持一個 NH Shelfie 入口**，行為跟著設定切換；不是在分享選單裡同時出現兩個 NH Shelfie。理由：符合「在設定裡切換」，選單也比較乾淨。代價：原本「跳回 App」的路徑中間多了一個轉手，需要重新實機驗收。
3. **「直接收藏」的書，要等下次打開 App 才會真的寫進資料庫、補上書名與封面。** 分享當下只是記在手機的「收件匣」並顯示提示。理由：不開 App 就動資料庫有毀損風險（見 2.4）。「重複收藏」的判斷用的是一份 ID 清單快照，極少數情況（例如剛刪書就被系統關掉 App）提示可能不準，但資料不會錯。
4. **（使用者已決定，2026-11-14）收藏頁的資料夾篩選選單保留 ≡ 和 ⋯**，和現在一樣可以直接在那裡拖曳排序、改名、刪除。設定頁另外新增「管理資料夾」，兩邊功能相同、結果互相同步。為了讓順序一致，**分隔線在篩選選單裡也有 ≡ 和 ⋯**（可以拖、可以改名或刪除，但不能勾選）。篩選選單最下方另放一個「管理資料夾」捷徑（新增分隔線從那裡進去）。兩邊共用同一份「改名／刪除」程式，不各寫一份。
5. **新加入的書預設放進「未讀」；現有的書一律不標成未讀。** 升級時會把「未讀」加進新增頁「上次選的資料夾」一次（之後取消勾選會被記住）。CSV 舊檔匯入的書也不標未讀。理由：「未讀要手動移除」代表書一開始就該在未讀裡；但把舊的上千本全部變未讀沒有意義。

**系統資料夾**

6. 「典藏」的其他語言：簡中「典藏」、英文「Favorites」、日文「お気に入り」。「未讀」：「未读」／「Unread」／「未読」。

## 5. 需要使用者在實機上手動測試的項目

> 安裝方式：推到 GitHub 後，從 Actions 的 Artifacts 下載 APK，**直接覆蓋安裝**（不要先解除安裝）。測試前建議先在舊版匯出一份 CSV 留底。

**升級（階段 A 之後）**

- [ ] 從 v0.3.0 覆蓋安裝後，原本的書、資料夾、備註、封面都還在，順序沒變
- [ ] 資料夾篩選最上方依序是：全部、未分類、未讀、典藏；未讀與典藏一開始都是 0 本
- [ ] 新加入一本書（不選任何資料夾）：同時出現在「未分類」和「未讀」
- [ ] 把一本書只加進「典藏」：它仍然算在「未分類」裡
- [ ] 把一本書加進自己建的資料夾：它從「未分類」消失，但還在「未讀」
- [ ] 在「未讀」裡點 ⋮ →「從『未讀』移除」，或長按多選後「從此資料夾移除」：書離開未讀，其他資料夾不受影響
